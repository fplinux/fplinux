title: Packaging

`./fplinux package` builds or reuses Release builds for the published phone set and creates one runnable ZIP each for Linux x86-64 and Windows x64, with one matching source ZIP. Users follow [Standalone archive](/fplinux/guides/standalone-archive/).

## Create a distribution

Prepare the dependencies, then run the package command:

```sh title="PC"
./fplinux setup --all
./fplinux package
```

After restoring the complete [dependency snapshot](/fplinux/guides/dependencies/), use `./fplinux setup --offline` to prepare the build environment from those inputs. A target with `publish = false` in its `release/manifest.toml` is available through explicit selection. To package only Konrow for Linux:

```sh title="PC"
./fplinux setup konrow-senior-280-plus
./fplinux package --target konrow-senior-280-plus --host linux
```

`--target TARGET` limits the models built and included. `--host linux` or `--host windows` creates only that host's ZIP. For a single target, run setup for each desired host as described in [Select setup inputs](/fplinux/start/build/#select-setup-inputs). Package builds use the same source snapshot and exclude prepared phone data.

Runtime ZIP names are `FPLinux-linux-x64-<release_id>.zip` and `FPLinux-windows-x64-<release_id>.zip`. Both use `FPLinux-<release_id>-sources.zip` from the same distribution, alongside `RELEASE.json` and `SHA256SUMS`. The twelve-character release ID appears in Settings → About → Build. A clean checkout uses the first twelve characters of its Git commit. Changed public sources get a content-based ID.

By default the files go under `out/releases/<release_id>/<all|TARGET>/<both|linux|windows>/` in the [working data directory](/fplinux/start/build/#working-data-directory). Keep each selection's runtime and matching source ZIP together. `--output-directory PATH` selects the exact directory. Use a new directory or one that already contains the identical distribution.

Each runnable ZIP includes the RAM system, selected phones' loaders and optional APKs, host Python and OpenSSH, a launcher, `README.txt`, licenses and checksums. For phones with a system-card profile, it also includes the components for installing and starting FPLinux from microSD. The launcher applies the phone's own data during installation. For manual card writing, `./fplinux build` with the card profile produces the complete `FPLINUX.img.xz` image. Follow [microSD system card](/fplinux/guides/microsd-system-card/) for both procedures.

## Complete releases

The workflow in `.github/workflows/packages.yml` prepares one inputs-only dependency snapshot for the event commit. The check, build and documentation jobs restore it before offline setup. The build job runs the same `./fplinux package` command and attaches the exact dependency inputs before uploading the distribution. The documentation job installs only its site tools with `setup --site --offline`.

A public Release includes the full distribution and the dependency transport parts of at most 1 GiB, their `FPLinux-<release_id>-inputs.sha256` index and `DEPENDENCIES.json`. The outer `SHA256SUMS` covers these assets too. Each runnable ZIP stores shared build data once. `DISTRIBUTION.json` in the source ZIP binds each target and host to the final runtime ZIP hash and that target's build identity.

Release validation requires the full published phone set for both hosts and matching dependency inputs. Native smoke jobs exercise model selection and launcher commands under ordinary Linux and Windows accounts without a phone. USB driver installation and loading a real phone require a device test.

The canonical repository publishes after the required check, build and native smoke jobs succeed. A push of a stable tag such as `v1.0.0` publishes FPLinux 1.0.0 as Latest. The tag must match the checkout's `VERSION` and resolve to the exact commit used for the verified distribution. Stable release notes compare with the previous published stable version. A push to `main` publishes a `build-<release_id>` prerelease. A manual workflow run checks the assets without publishing.

The publisher uploads a private draft and verifies every remote asset's name, size and SHA-256 before making the Release public. A retry verifies an existing published set or uploads only missing matching draft assets.

## Prepare a main push

Follow [Prepare an exact commit before pushing](/fplinux/guides/dependencies/#prepare-an-exact-commit-before-pushing) for the explicit clean-install command and local hook setup. The release pipeline independently acquires one complete input set for its event commit; publication depends on the resulting checks and final assets.

## Inspect artifacts

```sh title="PC"
./fplinux inspect source
./fplinux inspect bundle nokia-ta1618
./fplinux inspect bundle nokia-ta1618 --path
./fplinux inspect bundle nokia-ta1618 --current-source
./fplinux inspect archive path/to/FPLinux-linux-x64-….zip
./fplinux inspect distribution path/to/distribution
./fplinux inspect apk path/to/package.apk
```

- `source` shows the current public source snapshot and release identity without building.
- `bundle` lists the selected build's identity, files, sizes and SHA-256 hashes and checks them against its build manifest. `--path` prints only the absolute path of the selected generation for the given profile and build type. This mode checks the current pointer and manifest identity. Add `--current-source` to a full inspection to compare source, target workspace, environment receipt and signing identity separately. The receipt comparison does not probe installed environment content. Use `--without-device-data` or `--phone-data PATH` when the build used that selection. A stale bundle remains inspectable without the comparison.
- `archive` checks a runtime or corresponding-sources ZIP against its complete `SHA256SUMS` and manifest records. Source inspection also checks the source identity and selected build material. This establishes internal consistency, not authenticity or phone operation.
- `distribution` checks a packaged directory against its selected models and hosts, including its runtime and source association and any attached dependency inputs.
- `apk` shows a package's metadata and file list. It does not install the package, run its scripts or verify its signature.

These inspections need neither the build environment nor a phone.

## Measure image size

`inspect footprint` measures the current build without rebuilding it. Save a report before and after a source change and rebuild, then compare them:

```sh title="PC"
./fplinux inspect footprint nokia-ta1618 --json > before.json
# change the source and rebuild
./fplinux inspect footprint nokia-ta1618 --json > after.json
./fplinux inspect footprint-diff before.json after.json
```

The report lists boot files, the kernel, compressed and unpacked root filesystem, optional APKs and host debug files separately. These layers overlap, so their sum is not a meaningful total. A package's size counts the files it owns, not its dependencies, installed disk usage or RAM use. The diff also reports whether root filesystem content is identical; a smaller compressed image alone does not establish lower userspace or memory use.

A standalone archive runs FPLinux on one phone without a source checkout or build tools. Use an archive for your exact phone and PC operating system. Its `README.txt` names the phone, its boot key and startup commands. Check the phone's [support status](/fplinux/phones/#support-status) and [phone page](/fplinux/phones/) for feature, storage and power limits.

Autonomous archives include a short `README.txt`. Ordinary Linux runner archives also include `docs/index.html` for reading the site offline.

:::note[No release archive is published yet]

There are no published FPLinux release archives. You can package a phone-test candidate from your own build; see [Packaging](/fplinux/develop/packaging/). An archive with `CANDIDATE-NOTICE.txt` is such a candidate. It is for phone testing and must not be published as a release. Packaging it does not establish that it works on the phone. UMS9117 autonomous first-run preparation and subsequent loading have not been qualified on phone hardware. The Windows host workflow has not been qualified on native Windows.

:::

## Autonomous RAM archive

This format supports the default RAM profile. UMS9117 archives run on Linux x86-64 or Windows x64; Xiaomi Qin 1s+ archives run on Linux x86-64.

An autonomous archive contains the RAM image, phone loader stages, Python, OpenSSH, checksums and license notices. It contains no optional APKs or prepared phone data. The internal storage is never erased or written.

On UMS9117 targets that require runtime data, the archive also includes extraction tools. Its first run saves a read-only backup of the phone's internal storage and prepares firmware and audio data. Qin and headless UMS9117 targets without required runtime groups start Linux and open SSH immediately; no backup or data preparation is required.

### What you need

- A Linux x86-64 PC with coreutils, iproute2, udev and a network manager that automatically runs IPv4 DHCP on a new USB network interface, such as NetworkManager; or a Windows 10 or 11 x64 PC with Windows PowerShell.
- A USB data cable that fits your phone.
- For UMS9117, enough free space for the full internal-storage backup in the extracted archive directory.

Python and OpenSSH are bundled; no separate installation is needed. On Linux, the launcher asks for administrator access once if the included USB access rules need to be installed; this step requires `sudo`. On Windows, it can ask to install the included USB driver: read the displayed license, select its acceptance checkbox and approve the administrator prompt. Run the launcher as your regular user.

### First run

<Steps>

1. Extract the whole archive and keep the phone powered off and disconnected.

2. Start the launcher from the extracted directory. On Linux:

   ```sh title="PC"
   sh Run.sh
   ```

   On Windows, double-click `Run.cmd`.

3. Wait until the launcher displays the connection instructions. Only then hold the boot key named in `README.txt` and connect the powered-off phone, keeping the key pressed.

4. On a target that boots directly, wait for Linux and the SSH shell. On UMS9117 with required runtime data, keep USB connected while the launcher saves the complete backup and prepares the data. The phone shows the reading progress and preparation stage. Wait until the launcher reports that your phone data is ready and confirms that storage is safe to disconnect.

5. After UMS9117 preparation, disconnect USB. If the phone stays on, briefly remove and reinsert its battery. Run the launcher again with the phone powered off; preparation does not start a second load automatically.

</Steps>

Private connection keys are kept in `data/session/`. UMS9117 preparation saves `data/nand.bin` with its geometry receipt `data/nand.bin.json`, prepared files in `data/phone/groups/` and reports in `data/phone/reports/`. If preparation fails after saving the backup, the next run reuses it. Keep the extracted directory for subsequent runs and treat its contents as [private phone data](/fplinux/guides/device-data/). Use it only with the same physical phone, even if another phone has the same model name.

Each launch prints the path to its `logs/<launch-id>/runtime.log`, with `run.json` metadata beside it. The log includes launcher and USB loader diagnostics, but does not record your interactive SSH commands or terminal output. If preparation cannot verify that storage is safe to disconnect, it retains reader keys in `data/reader/session/`. Keep the phone powered and retain those keys. Run the launcher again to reconnect and repeat the storage check; do not remove power while storage safety is unresolved. `--reconnect` requires a normal session and cannot reopen this preparation session.

### Subsequent runs

Use the same `sh Run.sh` on Linux or `Run.cmd` on Windows for every later launch. If your phone is still running FPLinux and connected, the launcher verifies its saved connection and opens SSH again. If that phone is absent, keep it powered off and disconnected until the launcher displays the connection instructions. Then connect it with its boot key held. The launcher loads FPLinux, including prepared data on UMS9117, and opens an SSH shell.

Type `exit` or press Ctrl+D to close the shell; Linux keeps running on the phone. Open the same launcher to connect again. Only one launcher can run from the same extracted directory at a time; close its active launch before opening another. A connection that is present but cannot be verified stops with an error instead of starting another load. Ctrl+C cancels loading or waiting, but does not power the phone off.

The matching `*-sources.zip` contains source and build material separately from the runnable archive. Keep it available alongside the runnable ZIP; component licenses remain in the runnable archive.

### Prepare from an existing backup

For UMS9117, you can prepare from a complete physical NAND backup of the same phone without connecting it. On Linux:

```sh title="PC"
sh Run.sh --from-dump /path/to/nand.bin
```

On Windows, open a terminal in the extracted directory:

```bat title="PC"
Run.cmd --from-dump "C:\path\to\nand.bin"
```

This preserves the input backup and finishes after preparing `data/phone/`. It refuses to replace phone data that is already prepared in this directory.

## Linux runner archive

An ordinary archive uses the same `fplinux.py` runtime as an autonomous archive, with Python and OpenSSH supplied by your PC. UMS9117 RAM archives use the same first-run preparation and reconnect procedure; Qin boots directly. If the archive includes prepared personal data, keep it private. You need Linux x86-64, Python 3.14, GNU `stdbuf` from coreutils, `ip` from iproute2, and `ssh`, `ssh-keygen`, `ssh-keyscan` and `sftp` from OpenSSH. A network manager must automatically run IPv4 DHCP on the phone's USB network interface.

The phone-side loader stages are included in the archive, including FDL1, FDL2 and SML for Qin.

### Prepare the PC

<Steps>

1. Extract the whole archive, enter its top-level directory and check every file:

   ```sh title="PC"
   cd <extracted-top-level-directory>
   sha256sum -c SHA256SUMS
   ```

2. Install the USB rules and reload them:

   ```sh title="PC"
   sudo install -m 0644 ./60-fplinux.rules /etc/udev/rules.d/60-fplinux.rules
   sudo udevadm control --reload-rules
   ```

   Disconnect the phone if it is attached. On a headless PC, edit your installed copy to use a local group with `MODE="0660"` instead of `TAG+="uaccess"`. Never make the USB devices world-writable.

</Steps>

`SHA256SUMS` checks that the extracted files are complete and unchanged. It does not show that the archive is authentic or that the phone works.

If the archive contains `FPLINUX.img.xz`, it boots from a microSD system card. Prepare the card first; see [microSD system card](/fplinux/guides/microsd-system-card/).

### Start a session

Run the runner as your regular user, not as root.

<Steps>

1. Power the phone off and disconnect USB.

2. Start the runner:

   ```sh title="PC"
   python3.14 -I fplinux.py run
   ```

3. Wait until it asks for the phone.

4. Only then hold the boot key named in `README.txt` and connect the powered-off phone, keeping the key pressed.

5. Follow the [first-run procedure](#first-run) if the target needs NAND preparation. On a normal boot, the runtime opens a shell when the session is ready. Repeat the same command to reopen a running session.

</Steps>

### Use the running phone

Exiting the shell does not stop Linux. Reconnect, run one command or copy files with `--reconnect`:

```sh title="PC"
python3.14 -I fplinux.py run --reconnect
python3.14 -I fplinux.py run --reconnect --exec 'uname -a'
python3.14 -I fplinux.py run --reconnect --upload ./song.wav /tmp/song.wav
python3.14 -I fplinux.py run --reconnect --pull /tmp/photo.jpg ./photo.jpg
```

On Linux, autonomous launchers accept the same options, for example `sh Run.sh --reconnect --exec 'uname -a'`. File transfer requires a Linux host; native Windows supports the SSH and NAND workflows. To add applications, see [Optional packages](/fplinux/guides/packages/). The feature pages describe how to use supported features from an archive.

For machine-readable progress during a fresh runner load, add `--events PATH`; see [loader events](/fplinux/start/run/#for-automation-loader-events).

## Connection order and shutdown

For a fresh RAM load, connect the phone only when the launcher or runner asks. If you connected it too early, disconnect it, power it off and start again. To reopen SSH to the same running phone, leave it connected.

Exiting a launcher or shell leaves Linux running. To end the session without losing data, follow [Power](/fplinux/use/power/). Without a battery, disconnecting USB cuts power immediately.
